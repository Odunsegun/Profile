Hotel Management System

A server-rendered staff portal for managing rooms, customers, services, and reservations in one workflow. It validates stay dates and room conflicts, calculates room and add-on charges, and produces printable itemized invoices.

  • Java 17
  • Spring Boot 3.2
  • Thymeleaf
  • H2

01

Overview

Problem & motivation

Reservation data becomes unreliable when customers, rooms, dates, and charges are managed separately. The application brings those records into one authenticated workflow while preventing conflicting confirmed stays for the same room.

My role

I completed the current full-stack redevelopment across the Thymeleaf screens, Spring MVC controllers, service-layer rules, JPA repositories, security configuration, and self-contained demo environment.

What was built

An authenticated staff portal with an operational dashboard, management screens for customers, rooms, and optional services, booking creation and editing, cancellation, and printable invoices.

  • Maintain customer, room, and optional-service records.
  • Create and edit bookings with date and room-conflict validation.
  • Calculate room charges, selected service costs, and the final invoice total.
02

Inside the Build

Interface
Thymeleaf renders the dashboard, management forms, booking tables, and printable invoice on the server.
Application
Spring MVC controllers receive form requests while service classes apply booking rules and coordinate related records.
Data
Spring Data JPA maps customers, rooms, services, and bookings to H2. Seed records make the demo immediately reviewable, and the in-memory data resets on restart.
Security
Spring Security requires authentication for operational routes and BCrypt-encodes the two in-memory demo-account passwords.

Engineering decision

Keep the demonstration self-contained

An in-memory H2 database and seed script remove external database setup from the review path. The tradeoff is explicit: records reset whenever the application restarts, so this is a demonstration environment rather than persistent production storage.

03

Challenges & Takeaways

Technical challenge

Date conflicts must be detected during both booking creation and editing. A simple room lookup can miss partial overlaps or incorrectly reject a reservation being edited.

How it was addressed

The repository checks confirmed stays whose start is before the requested end and whose end is after the requested start, while excluding the current booking ID during edits.

Specific takeaway

Data-integrity rules belong below the form because every request must follow the same constraints, regardless of which screen or action submitted it.

Future improvement

Add payment gateway integration. The current application calculates and prints invoice totals but does not collect or process payments.
