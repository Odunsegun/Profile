Vacation Finder

Vacation Finder is a collaborative university Flutter and Dart prototype that brings interactive maps, place details, directions, and travel-post data into one mobile project. I worked as a mobile developer on Firestore-backed post and location flows, post integration, English/French localization, and integration issues across the shared codebase.

01

Overview

Problem & motivation

Travel information often arrives through separate map, place, route, and post data sources. The prototype explores how those inputs can meet in one mobile project without presenting the result as a deployed product.

My role

As a mobile developer on the university team, I handled Firestore-backed post and location flows, integrated the post work, contributed English/French localization, and worked on integration issues across shared code.

What was built

The repository combines Flutter screens with OpenStreetMap rendering, device location, Google place/detail/direction services, cloud-backed post data, and local persistence dependencies. Service configuration is still required before treating those paths as runtime-verified.

  • Render map context with flutter_map and OpenStreetMap, with Geolocator available for device position.
  • Bring Places, place-detail, and direction service data into the Flutter project.
  • Connect post and location data to Firestore while contributing partial English/French localization.
02

Inside the Build

Interface
Flutter and Dart form the shared mobile prototype in which the post integration and cross-screen fixes were made.
Mapping
flutter_map renders OpenStreetMap tiles, while Geolocator is included for device-location context.
Services
Google Places, place details, and directions provide external location and route data; their runtime behavior depends on valid local configuration.
Persistence
Cloud Firestore supports post and location data paths, with SharedPreferences and SQLite also present as local persistence dependencies.

Integration decision

Work through the shared data paths

Rather than isolate the post work as a separate demo, I connected it to the collaborative Flutter codebase and worked through the localization and integration points around it. Because cloud and local persistence coexist, this case study names each dependency without implying one unified storage model.

03

Challenges & Takeaways

Technical challenge

Post and location work had to fit a shared mobile codebase that combined external map services, Firestore, local persistence, and localization resources.

How it was addressed

I concentrated on the Firestore-backed post/location flow, integrated the post work with the team project, contributed to English/French localization coverage, and worked on issues where those pieces met.

Specific takeaway

Mobile integrations are easier to reason about when external configuration, cloud data, local persistence, and user-facing language resources have clear boundaries.

Future improvement

Move service configuration out of source, replace the custom credential flow with a maintained authentication solution, consolidate post persistence, complete localization coverage, and replace the stale template test with project-relevant automated tests.
