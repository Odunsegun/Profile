Overview

Problem & motivation

Access-control mistakes can hide behind an ordinary interface. This local course project turns those mistakes into educational challenges so the security lesson can be observed without pointing at a real service.

My role

I authored and integrated one challenge across the static interface and Express server, worked through follow-up route changes, and produced a personal walkthrough documenting the completed local exercise.

What was built

The five-person project serves static HTML, CSS, and JavaScript through Express and groups several deliberately vulnerable web exercises. Confirmed team topics include browser-cache handling, exposed development content, client-controlled request data, and unsafe information boundaries.

  • Present local challenge pages and clues through a browser-based interface.
  • Connect client observations to intentionally weak Express request handling.
  • Document the security lesson with a manual walkthrough and sanitized evidence.
02

Inside the Build

Interface
Static HTML, CSS, and browser JavaScript provide the challenge pages, test surface, and team-authored clues.
Server
Node.js and Express serve the interface and implement the intentionally weak request branches used by the local exercises.
State
cookie-parser, browser Cache API usage, headers, queries, and form data create several deliberate trust-boundary lessons across the team project.
Analysis
My walkthrough uses Burp Suite to observe the local request flow. No captured request values or operational payloads are reproduced here.

Challenge-design decision

Make the lesson cross the client/server boundary

The authored scenario starts with evidence in an exposed test interface, but the meaningful failure sits in the server's acceptance of client-controlled debug context. That separation turns a hidden UI clue into a lesson about enforcing authorization on the server.

03

Challenges & Takeaways

Technical challenge

The exercise needed to be discoverable through careful observation while still teaching a real client/server trust failure instead of ending at a hidden visual control.

How it was addressed

I connected an exposed test surface to an intentionally weak Express branch, integrated the related pages into the evolving team application, and documented the reasoning in a personal walkthrough.

Specific takeaway

Client-side visibility is never authorization. Sensitive branches need server-side identity and policy checks even when their controls or routes are absent from the normal interface.

Future improvement

Run each challenge in a disposable environment, generate challenge values per session, remove debug surfaces from release builds, and add negative authorization tests for the remediated version.
